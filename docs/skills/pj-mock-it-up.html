pj-mock-it-up

Makes mockup variants for a UI change in an issue.

Input#issue. Optional: number of variants, a creative objective for each variant, or mutate vN with guidance.
RequiresAn open issue. Any state. A headless browser to render PNGs.
ResultNew variants on the attachments branch and a comment on the issue. The state does not change.

Steps

  1. Read the issue, its comments, the spec section, and the existing mockups.
  2. Find the screens, and the states of each screen that matter: empty, loading, error, filled.
  3. Start one subagent for each variant. Give it the spec, the screens and states, and its creative objective.
  4. Each subagent writes one responsive HTML file for each screen and state.
  5. Render each HTML file to PNG for each viewport.
  6. For each screen and state, join the viewport PNGs side by side into one sheet.
  7. Commit the files to attachments.
  8. Comment on the issue. For each variant, show the sheets inline and link the files.

Variants

  • Make 2 variants by default. Make a different number if the user asks.
  • The user can give a creative objective for each variant.
  • To mutate, the user names a variant and gives guidance. The result is a new variant. The base variant does not change.
  • Each run adds new variants: v1, v2, then v3, and so on. Do not overwrite a variant.
  • The human picks a variant. Grill records the pick as a human decision in the spec.

Viewports

PlatformViewports
Webmobile, desktop
Flutterphone and tablet, each in portrait and landscape

Fidelity

  • Mid fidelity. The goal is to agree on structure, not to finish the visuals.
  • Use the existing look of the app if the repo makes it clear. If not, use a neutral wireframe style.

Design direction

  • Before it writes HTML, each subagent commits to one direction.
  • With a creative objective: follow the objective. Bold visual directions are allowed.
  • With no objective: keep the look of the app. Variants differ in structure: layout, flow, interaction.
  • Before writing HTML, write a short plan: 4 to 6 named colors, the type roles, and an ASCII wireframe. Ask: "Would I make this for any similar brief?" If yes, change it.
  • Be bold in one place only. Keep the rest quiet.
  • Before rendering, check the HTML against the anti-patterns. Fix each hit.

Anti-patterns

Check each screen against this list before rendering. Fix each hit. The look of the app has priority: if the app already uses a pattern, keep it.

  1. Do not use Inter, Roboto, Geist, or Space Grotesk as the only typeface by default.
  2. Do not use purple or violet gradients, cyan on dark, or glowing colored shadows.
  3. Do not use a cream background by default, or a near-black background with one neon accent.
  4. Do not use gradient text. Do not color or italicize one word in a headline.
  5. Do not put a small uppercase label above each heading.
  6. Do not number sections (01, 02, 03) unless the content is a real sequence.
  7. Do not build the screen from identical rounded cards with the same radius and shadow.
  8. Do not put cards inside cards.
  9. Do not put a thick colored border on one side of cards, alerts, or list items.
  10. Do not use the feature card with an icon in a rounded tile above the heading.
  11. Do not open with a big number, a small label, and a row of stats, unless the spec asks for metrics.
  12. Do not use the same spacing everywhere. Group related items. Put more space above a heading than below it.
  13. Make the type hierarchy clear. Each size step is at least 1.25 times the previous one.
  14. Do not use emoji or Unicode symbols as icons. Use one icon set.
  15. Do not use lorem ipsum, buzzwords, or slogans. Write real content in the words of the product.
  16. Do not use vague button labels such as "Submit" or "Learn more". Name the action.
  17. Do not add decorative grids, stripes, blobs, glows, or clip-art scenes.
  18. Do not use grey text on colored surfaces, or text with low contrast.
  19. Keep padding at screen edges and in containers: 16 px minimum on mobile.

Sources: Anthropic frontend-design and pbakaus/impeccable, both Apache 2.0. The text here is our own.
