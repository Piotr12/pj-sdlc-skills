pj-decompose

Splits an issue that is too big into child issues.

Input#issue (the parent)
RequiresThe parent has spec-ready.
ResultChild issues under the parent. Each child has a spec and spec-ready.

Steps

  1. Read the parent spec from attachments at issues/<parent>/spec.md.
  2. If the parent already has children, show them and stop. Do not make duplicates.
  3. Split the work into slices. Show the plan to the user and wait for approval.
  4. Create one child issue for each slice.
  5. For each child, commit a spec to attachments at issues/<child>/spec.md.
  6. Set spec-ready on each child.
  7. Comment on the parent with a task list of the children.

Slicing rules

  • Each slice is vertical. It ships behaviour that a user or a test can see, not a layer such as "backend only".
  • Each acceptance criterion of the parent goes to exactly one child.
  • Each child fits in one pj-implement run. Use the same "too big" criteria as pj-implement.
  • Make slices independent when possible. If order matters, write Depends on #x in the child.
  • One level only. A child does not get children.

Parent

  • The parent keeps spec-ready. pj-implement refuses a parent that has children.
  • The parent comment holds a task list: - [ ] #12. GitHub shows the progress.
  • A human closes the parent when all children are closed. Agents do not close issues.

Links

  • Link each child to the parent as a GitHub sub-issue.
  • Also write Parent: #n in the child, so that an agent sees the parent in the issue body.

Related

  • pj-implement recommends this skill when the bite is too big. A human can also run it directly.
