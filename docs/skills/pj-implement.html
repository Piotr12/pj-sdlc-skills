pj-implement

Implements a spec-ready issue and opens a PR.

Input#issue
RequiresThe issue has spec-ready.
ResultA PR with Closes #<n>. The issue is then Implemented.

Steps

  1. Check for spec-ready. If it is not there, stop and suggest pj-grill-for-specs-readiness.
  2. If the issue has children from pj-decompose, stop. Implement the children.
  3. Read the spec from attachments at issues/<n>/spec.md.
  4. Assess the size of the bite. If it is too big, recommend pj-decompose and stop. The user can override this.
  5. Work in the worktree .worktrees/<n> on the branch pj/<n>-<slug>. If it exists, continue in it. pj-repro can create it first. If not, create it and install the dependencies.
  6. Write the design to attachments at issues/<n>/design.md.
  7. Get an adversarial review of the design. Fix the blocking findings.
  8. Record each decision that is hard to reverse as an ADR in docs/adr/.
  9. Write the code and the tests.
  10. Update docs/ so that the docs show the new state of the system.
  11. Check the Definition of Done.
  12. Save the evidence to attachments at issues/<n>/evidence/.
  13. Open the PR.

Too big

The limits come from biteSize in .pj/config.json: 7/400, 8/800, or 9/1600. The bite is too big if one of these is true. pj-decompose uses the same criteria.

  • The spec has more acceptance criteria than the limit.
  • The estimated diff has more lines than the limit. Do not count tests or generated code.
  • The issue has parts that can ship on their own.

Design

Make the design as short as the change allows. A small change needs a few lines.

## Approach            how, in a few sentences
## Changes             modules and files to change
## Data model          the delta, as a Mermaid diagram (if any)
## Test plan           acceptance criterion → test; key logic for mutation tests
## Docs                files in docs/ to update; ADR candidates
## Risks               security, access, performance, migration, failure modes

Design review

  • Run the review in a subagent with a fresh context. Use a different model if one is available.
  • The reviewer gets the spec, the design, and docs/. It does not get the reasoning of the author.
  • Rubric:
    1. Does the design cover each acceptance criterion and each edge case?
    2. Is there a simpler approach?
    3. Does it conflict with the data model or an ADR?
    4. Are the risks handled?
    5. Will the tests in the test plan catch a real bug?
  • Each finding is blocking or non-blocking.
  • Maximum 2 rounds. If blocking findings remain after round 2, comment on the issue with the design and the findings, and stop.

Definition of Done

  • Each acceptance criterion has at least one test.
  • Build, lint, and tests pass. Use the commands from the Project section of AGENTS.md.
  • Mutation tests ran on the key logic that changed. Kill each mutant that survives, or explain it in the PR.
  • docs/ is up to date.
  • The code follows the rules in AGENTS.md.
  • UI change: screenshots at the same viewports as the mockup.

Pull request

Closes #<n>

Spec · Design · Evidence          (links to attachments)

## Acceptance criteria            (checklist, each with its test)
## Agent decisions                (made during implementation)
## Surviving mutants              (if any, with the reason)

Rules

  • Never change the issue labels.
  • Small deviation from the spec: record it under Agent decisions in the PR.
  • A deviation that changes an acceptance criterion: comment on the issue and stop. A human decides.
  • If you cannot get to a PR: push the branch, comment on the issue with the reason, and stop. Do not open a draft PR.

Devlog

At the end of the run, append one entry to the devlog. Also append one if the run stops early.
