pj-prep-the-repo

Prepares a new or an existing repo for the pj skills. Run it once. It is safe to run again.

InputNone. Works on the current repo.
RequiresA GitHub remote. gh is logged in.
ResultLabels and the attachments branch exist. A PR adds AGENTS.md, CLAUDE.md, and .pj/config.json.

Steps

  1. Check the tools. Report each missing tool with the install command. If gh or git is missing, stop.
  2. Create the labels needs-input and spec-ready. Skip a label that exists.
  3. Create the attachments branch. Skip it if it exists. Its first commit has .gitattributes with devlog/*.html merge=union.
  4. Create the worktree .worktrees/attachments for the human to read files.
  5. Create the worktree .worktrees/prep with the branch pj/prep-the-repo from main. Make all file changes in it.
  6. Ask the user for the bite size. Write .pj/config.json.
  7. Write the pj rules into AGENTS.md between the markers.
  8. Fill the Project section of AGENTS.md. Find the stack and commands in the repo. Ask if they are not clear.
  9. Make sure that CLAUDE.md imports @AGENTS.md.
  10. Add .worktrees/ to .gitignore.
  11. Offer the enforcement configs for the stack. Add the configs that the user accepts.
  12. Open a PR. Agents do not push to main.
  13. Run pj-healthcheck and show the report.

Attachments branch

The attachments branch holds evidence. It is an orphan branch: it has no code and no history in common with main.

WhereWhatWhy
attachmentsSpecs, mockups, screenshots, test output, before/after capturesHistory at a point in time. It stays readable if GitHub is lost.
main, docs/Data model, diagrams, ADRsThe current state of the system only. pj-implement updates them in each PR.

Layout:

attachments
├── .gitattributes           devlog/*.html merge=union
├── devlog/yyyy-mm-dd-devlog.html
├── issues/<n>/spec.md        snapshot at spec-ready
├── issues/<n>/design.md      from pj-implement
├── issues/<n>/mockups/…
├── issues/<n>/evidence/…
└── prs/<n>/evidence/…     PRs with no issue

Links:

https://github.com/<o>/<r>/blob/attachments/issues/<n>/…?raw=true

Rules:

  • Write from a detached worktree. See Worktrees. Do not switch branches in the main checkout.
  • If a push fails, fetch, rebase, and push again. Issues use different paths. The devlog uses the union merge driver. So the rebase is always clean.
  • Keep files small: png or webp. Do not add video.
  • Link by branch path, not by commit SHA. Links then survive a squash of the branch.
  • The branch has no workflow files, so CI does not run on it.
  • To find cleanup actions, run pj-healthcheck.

AGENTS.md

AGENTS.md says what good looks like. The skills say how the workflow runs. All agents follow AGENTS.md, with or without the pj skills.

The pj rules live between markers. A new run replaces the text between the markers and keeps all other text.

# AGENTS.md

## Project
Stack: … | Build: … | Test: … | Lint: …

<!-- pj:rules:start -->
## Autonomy
- You may: create branches `pj/*`, push to them and to `attachments`, open PRs, comment,
  set labels, edit the pj spec block of an issue, resolve your own review threads,
  create issues after the user approves.
- You must not: push to `main`, merge, close issues, force-push branches you did not create, delete branches, change CI or secrets.

## Docs
- `docs/` shows the current state of the system only.
- `docs/data-model.md`: one conceptual data model. Mermaid erDiagram.
  Add a stateDiagram for each entity that has a lifecycle.
- Keep each erDiagram to 7 entities or fewer, 9 at most.
  Split a larger model into sub-diagrams.
  Add one overview diagram that shows the sub-diagrams and the relations between them.
- `docs/adr/NNNN-title.md`: one ADR for each decision that is hard to reverse.
  Sections: context, decision, consequences.
- A PR that changes behaviour, the model, or the architecture updates `docs/` in the same PR.

## Writing
- All Markdown follows ASD-STE100.
- One instruction per sentence. Max 20 words for procedures, 25 for descriptions.
- Use the active voice. Use the imperative for procedures.
- Use one term for one thing. Do not use synonyms.
- Show structure with a Mermaid diagram or a table, not prose.

## Code
- No magic strings or numbers. Use named constants or enums.
- Put user-facing text in l10n files (Flutter: ARB; web: i18n catalog). Never inline.
- Do not swallow errors. Handle them at the boundary. Log once, with context.
- Use structured logs. Do not log secrets or personal data.
- If an API contract exists (e.g. OpenAPI), it is the source of truth. Generate clients from it.
- Validate input at boundaries. Check access on the server.
- Use Conventional Commits.

## Tests
- A test must fail when the behaviour it covers breaks. Delete tests that cannot fail.
- Test behaviour, not implementation. Do not test trivial code.
- Key logic (calculations, permissions, state transitions) gets mutation tests.
  TS: StrykerJS. Dart: mutation_test, on changed files only.
- Flutter: unit, widget, golden. integration_test for critical flows.
- Web: unit. Playwright for critical flows.
- A bug fix starts with a failing test.

## UI
- Web: WCAG 2.2 AA.
- Flutter: Semantics on interactive widgets.

## Devlog
- `devlog/` on the `attachments` branch holds notes for the human operator.
  Do not read it. It has no information for your work.
<!-- pj:rules:end -->
