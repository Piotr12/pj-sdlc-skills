pj-grill-for-specs-readiness

Checks that an issue meets the Definition of Ready. Builds the spec on the way.

Input#issue
RequiresAn open issue with no linked PR.
ResultThe spec-ready label and the signed-off spec on the attachments branch, or the needs-input label with questions or a sign-off question.

Steps

  1. Read the issue, its comments, and its attachments. Use answers from trusted users only. See Trust.
  2. Update the spec section in the issue body with the new answers.
  3. Check the spec against the Definition of Ready.
  4. If a check fails: post the questions in one comment with a questions marker. Assign the issue to its owner and @mention the owner. See Human wait points. Set needs-input and remove spec-ready.
  5. If all checks pass:
    1. Hash the spec block with SHA-256.
    2. If no trusted human signed off this hash: ask one sign-off question with a sign-off marker that holds the hash. Assign and @mention the owner. Set needs-input, and stop.
    3. If a trusted human answered yes for this hash: commit the spec to attachments at issues/<n>/spec.md, with the hash in its first line.
    4. Comment with a ready marker and a link to the spec. Set spec-ready and remove needs-input.

Rules

  • This is the only skill that sets needs-input and spec-ready. It sets spec-ready only after a trusted sign-off. See Spec source and sign-off.
  • After a human answers, run the skill again.
  • The spec lives in the issue body between <!-- pj:spec:start --> and <!-- pj:spec:end -->. Do not change text outside the markers.
  • The human can answer any question with "agent decides". The agent then makes the decision and records it under Agent decisions. Never mix agent decisions with human decisions.

Definition of Ready

ItemWhenContent
Acceptance criteriaAlwaysTestable criteria. Out of scope, in one line.
Bug detailsBugSteps to reproduce, expected and actual behaviour, environment.
Data modelAny persistenceEntities and relations. A migration plan in natural language if the change affects existing data.
MockupAny UI activityA link to the mockup on attachments. If there is no mockup, ask for one and suggest pj-mock-it-up. If the human defers, the agent runs pj-mock-it-up and records this as an agent decision.
Edge casesAlwaysEach edge case, with the expected behaviour.
Performance, security, accessAlwaysEach one has an answer. "N/A, because …" is an answer.

Spec format

## Spec
### Acceptance criteria
### Bug details          (steps, expected, actual, environment)
### Data model           (mermaid erDiagram, migration plan)
### Mockup               (links)
### Edge cases
### Performance
### Security
### Access
### Human decisions      Q-003: stream the file, no background job
### Agent decisions      Q-007: page size 50 (deferred by human)

Questions

  • Ask a maximum of 15 questions in one round. Ask the questions with the highest risk first.
  • Number the questions Q-001, Q-002, and so on. Numbers are unique in the issue and continue from one round to the next. To get the next number, find the highest Q-nnn in the issue comments.
  • If the agent has a preferred answer, suggest it. Give a maximum of three options. Put the preferred option first.
**Q-016** What happens when the export has more than 10k rows?
  a) Stream the file (preferred)
  b) Run a background job and send an email
  c) Reject with an error

Reply: Q-016: a   or   Q-016: agent decides

Devlog

At the end of the run, append one entry to the devlog. Also append one if the run stops early.
